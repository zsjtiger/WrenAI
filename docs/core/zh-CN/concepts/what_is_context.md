# 什么是上下文？

上下文决定了智能体是"能看到你的数据库"，还是"能理解你的业务"。

Schema 告诉智能体某张表有哪些列。上下文则告诉它哪张表是权威的、各列是什么含义、哪些关联是获得批准的、公司信任哪些定义，以及过去什么做法有效。

这种区别很重要，因为 AI 智能体在业务数据上出错，并不只是因为它们不够聪明，而是因为它们所需的含义分散在数据仓库、仪表盘、SQL 文件、文档、幻灯片、Slack 讨论串和人们的脑海之中。

Janus AI 的存在，就是为了把这些分散的含义整合成一个开放的、机器可读的上下文层，供人类、智能体、仪表盘和应用共享。正是这一层让 **CReport**（即你的智能体生成的答案和仪表盘）变得可信，而不只是看似合理。

## 为什么仅有 Schema 不够

你的智能体能看到 Schema：它能读取列名、识别类型，甚至可能解析你已经维护的指标定义。但 Schema 无法讲清全部的故事：

- `status = 4` 表示已退款
- `loyalty_v3` 是你的团队实际使用的表
- "月活跃用户"不包括服务账号
- "Project Lighthouse" 对应 `campaign_id = 4172`
- 有些关联是获得批准的，而另一些会产生误导性的数字
- 有些问题在编写任何 SQL 之前就需要先澄清

没有这些上下文，智能体就只能猜测。它会挑选一张看似合理的表，写出看似合理的 SQL，然后返回一个看似合理的答案。演示时可能一切正常，而生产环境才会暴露缺失的含义。

**AI 智能体在业务数据上的瓶颈在于上下文，而不在于智能。**

## 上下文的五个层次

要让智能体在真实公司数据上回答真实的业务问题，它需要五个层次的上下文：

| 层次 | 回答的问题 | 示例 | 状态 |
| --- | --- | --- | --- |
| **结构层** | 存在哪些数据？ | 表、列、类型、键、关系 | 已可使用 |
| **语义层** | 数据意味着什么？ | 模型、指标、计算字段、枚举标签、标准表 | 已可使用 |
| **业务层** | 这家公司如何定义？ | 活跃客户、收入、流失、内部项目名称、团队特定的定义 | 已可使用 |
| **操作层** | 应如何安全地使用这些数据？ | 获批的关联路径、被允许的查询、查询时治理、禁止计算的内容 | 积极开发中 |
| **行为层** | 过去什么做法有效？ | 成功的自然语言到 SQL 的配对、示例、反馈、记忆 | 积极开发中 |

第一层让智能体能够读取数据库，接下来两层让它理解业务，最后两层帮助它安全地行动并随时间改进。

这些层次共同构成上下文层。

## 上下文与语义层

"语义层"是业界对 dbt Semantic Layer、Cube、LookML 等工具的称呼。它们定义面向业务的模型、关系、计算和可复用的逻辑，使人和工具无需直接查询原始表。这项工作非常重要，也是上下文的重要组成部分；在 Janus AI 中，这些语义定义存放在 MDL 中。

上下文层的范围更广。在语义定义之外，它还补充了自主智能体在真实世界中表现良好所需的知识：

- 哪些定义是可信的
- 应优先使用哪些表
- 哪些值代表什么含义
- 允许哪些关联
- 何时应请求澄清
- 哪些过往示例应指导下一次查询
- 如何校验、重试、修复和评估生成的 SQL

语义层主要是为仪表盘和 BI 工作流设计的。上下文层则面向这样一个世界：智能体、应用和人类都需要通过不同的接口获得同一个可信答案。

## Janus AI 如何表示上下文

Janus AI 并不把上下文视为单一的提示词或隐藏的产品功能，而是将其存储为显式的、可审阅的组成部分。

### MDL：语义契约

[建模定义语言（MDL）](/oss/concepts/what_is_mdl)是核心的语义契约。它以团队可以阅读和版本化的文件，描述模型、关系、计算字段、视图以及面向业务的结构。

MDL 帮助智能体把"按收入排名的头部客户"这样的问题映射到正确的模型、关联和计算，而不必从原始数据仓库结构中重新推导逻辑。

### 知识规则：业务与操作指导

`knowledge/rules/` 下的业务规则记录了那些未必适合放在模型定义中的指导内容：首选术语、默认过滤条件、表选择规则、注意事项，以及智能体应遵循的策略。

业务含义正是在这里开始转化为操作指导的。智能体不仅被告知有什么，还被告知团队期望如何使用这些数据。

### 查询与记忆：不断积累的示例

大多数 text-to-SQL 系统都把每个问题当作第一次遇到的问题。Janus AI 增加了[记忆层](/oss/concepts/memory_system)，使已完成的工作能够改进后续工作。

记忆有两项职责：

- **Schema 上下文检索**：为 MDL 和 `knowledge/rules/` 建立索引，然后为每个问题检索相关的模型、列、关系和指导。
- **查询召回**：存储经过确认的自然语言到 SQL 的配对，使类似的未来问题能够使用经过验证的示例。

这把使用过程转化为一个学习闭环。随着团队提出、纠正和确认更多问题，上下文层会变得越来越有用。

### 技能：可重复的智能体工作流

[技能](/oss/reference/skills)为 AI 编码智能体提供与 Janus AI 协作的结构化工作流。它们引导智能体完成可重复的操作（例如入门引导、生成 MDL、校验上下文和安全查询），而不是让智能体即兴发挥每一步。

技能之所以重要，是因为上下文不只是数据，还包括流程：何时检查、何时校验、何时询问、何时保存，以及何时停止。

## 上下文带来什么

当上下文是显式且共享的，同一个受治理的层可以服务于许多场景：

- **AI 智能体**可以查询业务数据，而无需自行发明关联或指标。
- **数据团队**可以把定义保存在受版本控制的文件中，而不是分散在各种提示词和仪表盘设置里。
- **业务用户**可以获得能够追溯到经过批准的模型和定义的答案。
- **产品团队**可以在面向客户的应用中嵌入分析，而无需构建一次性的数据逻辑层。
- **平台团队**可以通过范围更窄、更易治理的接口，为智能体开放数据访问。

最终目标不仅仅是更快的答案，而是团队可以信任的、更快的答案。

## 正确性需要一套系统

上下文是基础，但要保证正确性，还需要围绕它构建一整套系统。

可靠的 text-to-SQL 依赖多个基本能力协同工作：

- **Schema 关联（Schema linking）**：为问题找到正确的模型和列。
- **值画像（Value profiling）**：了解数据中实际出现了哪些值。
- **歧义检测（Ambiguity detection）**：判断问题何时需要澄清。
- **生成轨迹（Generation trace）**：展示答案是如何构建的。
- **重试与修复（Retry and repair）**：在首次尝试失败时进行恢复。
- **评估（Eval）**：随着定义和 Schema 的变化检测回归。

Janus AI 将这些能力作为智能体可以编排的基本原语开放出来，而不是把正确性隐藏在封闭的产品之中。更深入的说明请参见 [Janus AI 如何防止智能体产生幻觉？](/oss/concepts/correctness)，技术细节请参见[架构](/oss/reference/architecture)。

## 上下文从哪里来

上下文的第一版通常来自数据库本身。Janus AI 可以根据表、列、类型和关系生成 MDL 脚手架，使智能体快速获得可用的结构和语义基础。

更深层的上下文来自其他各处：

- 分析师编写的 SQL
- 业务术语表
- 指标定义
- 入职文档
- 产品规格
- 幻灯片和战略文档
- 过去的问题和已采纳的答案
- 人工纠正与审阅

因此，Janus AI 围绕"**快速搭建，然后深度丰富**"的工作流进行设计。先从结构入手，再引入使答案变得可信的业务含义。

## 简而言之

- **Schema** 告诉智能体有什么。
- **语义定义** 告诉智能体数据意味着什么。
- **上下文层** 告诉智能体业务如何使用数据、如何安全地行动，以及过去什么做法有效。

Janus AI 是面向 AI 智能体的开放上下文层：可移植、可检查、可版本化，并可被每一个需要可信业务数据的智能体和应用共享。
