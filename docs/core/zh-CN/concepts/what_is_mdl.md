# 什么是建模定义语言（MDL）？

建模定义语言（Modeling Definition Language，MDL）是 Janus AI 的核心语义契约。

它告诉智能体、应用和人类：你的业务数据意味着什么，包括存在哪些数据集、暴露哪些字段、实体之间如何关联、哪些计算可以复用，以及哪些查询形态的对象应被视为稳定接口。

原始 Schema 描述的是存储方式，MDL 描述的是含义。智能体生成的每一个受治理答案都会通过这份契约进行规划，它部署的每一个 CReport 仪表盘也是如此。这就是 MDL 位于核心的原因。

## MDL 为何存在

数据仓库是为存储数据的系统而优化的，而不是为了让人和智能体理解业务。

数据仓库可以告诉智能体某张表有一个名为 `status` 的列，却无法说明 `status = 4` 表示已退款。它可以暴露 `loyalty_v3`，却无法解释这是权威的会员表。它可以展示外键，却不一定给出分析团队信任的关联路径。

没有 MDL，每个智能体、仪表盘、SQL 脚本和嵌入式分析功能都必须从原始结构中重新推导同样的逻辑。这会导致定义重复、指标不一致、SQL 脆弱，以及没有人完全信任的答案。

MDL 把重要的部分显式地表达出来，把业务逻辑转化为团队可以审阅、版本化和共享的文件。

## 上下文层中的 MDL

Janus AI 是面向 AI 智能体的开放上下文层。MDL 是核心层，结构、语义和业务含义都在这里变得机器可读。

在五层上下文模型中，MDL 承载前三层：

| 上下文层 | MDL 如何提供帮助 |
| --- | --- |
| **结构层** | 定义智能体可以使用的数据集、列、类型、键和关系。 |
| **语义层** | 为原始数据仓库对象赋予面向业务的名称、描述、计算、视图和 Cube。 |
| **业务层** | 捕获权威表、可复用的指标、关系含义以及约定的分析接口。 |

操作指导和行为记忆与 MDL 一起存在于项目指令、技能和记忆层中。它们共同为智能体提供安全查询和随时间改进所需的更广泛上下文。

## MDL 定义了什么

MDL 对数据面向业务的形态进行建模。Janus 项目将这些定义存储为可读的 YAML，并编译为引擎可用的 `target/mdl.json` manifest。

核心 MDL 对象包括：

- **模型（Models）**：由物理表或 SQL 定义支撑的逻辑数据集。
- **列（Columns）**：对外暴露的字段，包括重命名字段、表达式、主键和计算字段。
- **关系（Relationships）**：模型之间可复用的关联逻辑。
- **计算字段（Calculated fields）**：只定义一次、在多个查询中复用的业务逻辑。
- **视图（Views）**：行为类似稳定虚拟表的命名 SQL 语句。
- **Cube**：带有度量、维度、时间维度和层级的结构化聚合对象。

每个建模对象的完整字段说明，请参见 [MDL Schema 参考](/oss/reference/mdl)。

## MDL 作为契约

"契约"一词很重要。

MDL 不只是文档，它是数据团队、智能体与查询引擎之间的约定。

- **对数据团队而言**，MDL 是一个可供审阅的、定义业务逻辑的地方。
- **对智能体而言**，MDL 是用于选择模型、关联和计算的结构化上下文。
- **对应用而言**，MDL 是在不断变化的数据仓库结构之上的稳定接口。
- **对引擎而言**，MDL 是针对底层数据源规划建模 SQL 的事实来源。

契约发生变化时，你可以审阅差异。查询运行时，Janus AI 可以依据契约进行规划。另一个智能体加入工作流时，它不需要从零开始学习业务。

## MDL 如何帮助 AI 智能体

AI 智能体擅长模式匹配，但原始 Schema 留下了太多解释空间。MDL 缩小了这一空间。

借助 MDL，智能体可以：

- 将业务问题映射到正确的建模数据集
- 优先使用权威表，而不是遗留表或 staging 表
- 遵循已定义的关系，而不是自己发明关联
- 复用已批准的计算，而不是创建一次性指标
- 将视图和 Cube 作为稳定的分析接口进行查询
- 将检索和 text-to-SQL 规划建立在显式的业务结构之上

结果并不是神奇的准确性，而是更好的依据。MDL 让智能体少一些猜测的理由。

## 为什么文件很重要

MDL 以文件的形式存在，是因为业务上下文应当可以移植。

你的定义不应被困在某个 BI 工具、某段提示词或某家供应商的 UI 中。它们应当易于检查、提交、审阅、分叉，并能跨环境部署。

Janus 项目把应随项目一起移动的部分与属于某个环境的部分区分开来：

- 模型、视图、关系、Cube 和指令存放在项目中，可以进行版本控制。
- 连接 profile 存放在项目之外，因此凭据和环境相关的设置不会泄露到共享文件中。
- 编译生成的 `target/mdl.json` 派生自源 YAML，随时可以重建。

项目结构与生命周期命令，请参见[管理项目](/oss/guides/manage_project)。

## 从原始 Schema 到可信上下文

MDL 通常从脚手架开始。`generate-mdl` 指南可以检查数据库、规范化类型、检测结构并生成初始项目，使智能体能够快速通过建模层进行查询。

这只是第一步，更深的价值来自团队对模型的持续丰富：

- 添加描述和业务名称
- 清晰标记主键和关系
- 定义可复用的计算
- 为常见分析路径发布视图
- 为受治理的聚合定义 Cube
- 隐藏或避免暴露不应对外的字段
- 记录权威数据源和业务规则

这与 Janus AI 整体工作流的理念一致：**快速搭建，然后深度丰富**。

## MDL 与执行

MDL 不只是用于提示词的元数据。Janus AI 在 SQL 规划阶段使用 MDL。

当查询引用建模对象时，Janus AI 会将这些模型、关系、计算字段和视图展开为目标数据源可执行的 SQL。Rust 语义引擎是 MDL 语义如何映射为 SQL 的权威实现。

这一点很重要，因为智能体的可靠性不仅取决于能否生成 SQL 文本。查询需要依据团队已经达成一致的同一套定义进行规划。

关于规划与执行的工作方式，请参见[架构](/oss/reference/architecture)。

## 简而言之

- **Schema** 描述数据如何存储。
- **MDL** 描述数据应当如何被理解和查询。
- **上下文** 将 MDL 与指令、记忆、技能和治理结合起来，使智能体能够可靠地运作。

MDL 是 Janus AI 持久的语义契约：人类可读、智能体可用、引擎可强制执行，并可在每一个需要可信业务数据的应用之间移植。
