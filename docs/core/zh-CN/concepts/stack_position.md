# Janus AI 在我的技术栈中处于什么位置？

> Janus AI 不会取代你的数据仓库、转换流水线或现有的语义层。它位于**数据基础设施与查询它的智能体之间**，提供智能体所需的上下文，以便安全地生成和部署可信的 BI。

## 简要说明

```text
┌──────────────────────────────────────────────────────┐
│   Your AI agents (Claude Code, Cursor, custom apps)  │
└────────────────────────┬─────────────────────────────┘
                         │  ask questions, get context
                         ▼
┌──────────────────────────────────────────────────────┐
│              Janus AI - open context layer            │
│   MDL · Memory · Skills · Governed execution         │
└────────────────────────┬─────────────────────────────┘
                         │  planned, governed SQL
                         ▼
┌──────────────────────────────────────────────────────┐
│   Your warehouse, transformation pipeline, files     │
│   (PostgreSQL, BigQuery, Snowflake, DuckDB, ...)     │
└──────────────────────────────────────────────────────┘
```

位于 Janus AI 之上的是提出问题的**智能体**，位于其之下的是存储答案的**数据基础设施**。Janus AI 则是中间的那一层，它把"我能看到 Schema"转变为"我理解业务含义"。

## 它不会取代什么

**你的数据仓库。** Janus AI 不存储数据行，数据仍然保存在你的数据仓库中。Janus AI 只是把规划好的 SQL 发送到那里执行。

**你的转换流水线。** 如果你已经使用 dbt、自定义 Python 或定时 SQL 把原始数据加工成整洁的表，请继续保持。Janus AI 读取的是处理后的结果，它不负责上游流水线。

**你现有的语义层。** 如果你已经有面向业务的模型、指标或指标层，Janus AI 可以在其之上叠加，让智能体无需重建即可获得相同的定义。你编写的 MDL 是**面向智能体的契约**；你已有的内容则留在原处。

**你的 BI 或仪表盘工具。** Janus AI 面向自主的使用者（智能体、脚本、嵌入式应用）构建。仪表盘可以继续使用你现有的工具。

## 它提供什么

**面向智能体的上下文层。** 五个层次（结构、语义、业务、操作、行为）被汇集到一个可检查、受版本控制的界面中，任何智能体都可以查询它。

**受治理的 SQL 平面。** CLI 将建模 SQL 规划为可执行的 SQL，运行 dry-plan / dry-run，应用访问策略，并通过你的数据仓库连接器执行。智能体不需要直接的数据库凭据，也不需要不受限制的访问权限。

**智能体原生的接口。** 技能、面向主流智能体框架的 SDK，以及专为由 LLM 驱动的编码智能体操作而设计的 CLI。这些都不需要额外维护新的 UI。

## Janus AI 如何适配你已有的技术栈

### 你没有语义层

从 Janus AI 的上下文层开始。`generate-mdl` 指南可以在几分钟内根据你的数据仓库 Schema 生成 MDL 项目，这是你的第一组可信语义定义，其余的上下文层（`knowledge/rules/`、记忆、治理）会围绕它们逐步生长。之后可以通过追问 / 自动驾驶工作流持续丰富它。

### 你有转换流水线（dbt、Coalesce、内部自研）

保留它。把 Janus AI 指向你流水线的**输出表**。MDL 描述这些表面向智能体的含义：应暴露哪些列、允许哪些关联、哪些计算可以复用。流水线继续负责数据摄取和建模逻辑，Janus AI 则负责已建模数据与智能体之间的那一层。

### 你有语义层

Janus AI 不会与数据团队的语义层竞争。它的上下文层通过智能体可以读取和推理的结构，把相同的定义提供给**智能体**：MDL 文件、结构化检索、过往答案的记忆，以及受治理的执行原语。可以把它看作你已有语义层在智能体端的原生投影。

### 你有多个数据仓库

Profile 将连接凭据与项目定义分离。同一个 MDL 项目可以绑定到开发、预发布和生产环境的 profile。MDL 保持可移植，凭据由 profile 承载。

## Janus AI 不适合的场景

- **你只需要一个由聊天驱动的 BI 应用。** Janus AI 是底层原语层，而不是聊天 UI。如果你想要现成的对话式仪表盘，商业版 Janus AI 或其他厂商的产品会更合适。
- **你希望完全不做 Schema 建模。** 即使是脚手架步骤也需要一些人工审阅。如果要求是"全自动、无需审阅"，任何上下文层都不会给出诚实的承诺。
- **你主要查询非结构化文本。** Janus AI 专注于结构化业务数据。基于文档的 RAG 是另一类问题。

## 为什么是"分层，而非替代"

为了让 AI 智能体更好地查询你的技术栈而替换整个技术栈，往往会让所有人都不满意。Janus AI 的设计思路恰恰相反：**保留现有技术栈，在其上增加一个可检查的层，为每个智能体提供同一套受治理的接口**。

业务上下文过于重要，不应被锁在某个供应商的产品之中。你的 MDL、示例、查询历史和映射决策都应保存在你的仓库中，接受你团队的审阅。
